# The generated skill: exact shape

What Step 8 writes. This is the contract for every skill this creator produces, whatever the use case.

## Folder shape

```
<their-skill-name>/
├── SKILL.md
├── references/
│   ├── rules.md              # hard rules + answered taste defaults
│   ├── sources.md            # their references (theirs first, then researched)
│   ├── input-contract.md     # what comes in, what to extract, what to do when it's missing
│   └── self-improvement.md   # copied from this skill, file names adapted
└── assets/
    └── templates/            # the 2-4 brand-adapted templates from Steps 3-7
```

Name the skill after the user's use case, lowercase-hyphenated: `acme-carousels`, `acme-launch-emails`. Never name it after this creator.

## Frontmatter: name and description only

```yaml
---
name: <their-skill-name>
description: <what it produces, in whose brand, from what inputs> Use whenever the user <trigger phrases from their actual vocabulary, including the ways they asked during creation>.
---
```

Nothing else in the frontmatter. No other keys - a generated skill that declares tool restrictions or extra metadata breaks portability across surfaces. The description is the trigger mechanism: make it a little pushy, name the input types from the input contract, and include phrasings that never say the word the use case is named after (someone wanting a carousel says "turn this into slides").

## SKILL.md body: the six required parts

1. **The one-paragraph job.** What this skill produces, that the design system at `design-system/` is its source of brand truth, and that a missing design system means stop and route to design-system-creator or firecrawl-brand-extractor - the gate survives into every generated skill.
2. **The input contract.** From Step 5: each expected input type, what to extract from it, what to fetch when something is missing. Plus: an unrecognized input means ask, not improvise.
3. **The build steps.** Read rules.md, pick the matching template from assets/templates/, fill it from the input, resolve every value from the design system's tokens. Where the use case has a copy structure (a hook arc, slide budgets, a survival checklist), state it here - lifted from the matching use-case file, trimmed to what this user's outputs need.
4. **/design gate 1 - variations.** Before the final build: 2-3 structurally distinct variations on a /design canvas (light and dark when applicable), each labeled with its case and tradeoff, plus a recommendation. The user picks or iterates.
5. **/design gate 2 - delivery.** The final output always lands on a /design canvas. The canvas is the deliverable; the user edits and exports (PNG/PDF) there. Fallback to files only when /design is unavailable, stated out loud.
   Both gates carry the live-artboard rule: every artboard is live HTML/CSS with all text as real editable elements styled with the brand tokens - never a flattened PNG or screenshot placed on the canvas. Generated imagery appears only as image layers inside an HTML artboard, type kept in HTML on top.
6. **The self-improvement clause.** The blockquote from `self-improvement.md`, pointing at this skill's own files.

Keep the generated SKILL.md lean - under 150 lines, plain sentences, the same smart-but-tired tone. Details go in the references files.

## Templates

- Every brand value in a template is a token or CSS variable resolved from `design-system/` - grep the templates for hardcoded hex values before writing them, and fix any you find.
- Light and dark variants come from one source wherever the use case has both, so a fix cannot miss a mode.
- Real third-party app logos come from the svgl.app API (see sources.md), never redrawn.
- The user's logo, if the design system has one, is placed in code - never generated by an image model.

## rules.md

Start it with what the creation session learned:

- The answered taste axes as defaults ("Density: dense - answered during setup").
- Any hard rules the user stated, verbatim.
- The never-guess rule: new unclear taste = AskUserQuestion with 2-4 concrete options; brand values = design system or an explicit user answer, never invented.

## Before handing over

- Run the skill's own flow once mentally against the Step 6 example: would it reproduce the approved output? If a step only works because you remember the session, the missing knowledge goes into a file.
- Confirm the install path with the user and state it in the close-out, with the file list.
- Tell them the one-line way to run it next time: invoke the skill by name with their usual input.
